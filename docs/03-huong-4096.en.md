# The 4096 direction — the entire switch group, DISABLED

*English translation of [03-huong-4096.md](03-huong-4096.md), which is extracted from
`src/sample_mm.cpp`. Function addresses are kept exactly as in the source so they can be
cross-checked. If the two versions disagree, trust the Vietnamese.*

> **None of this is enabled.** It is documented so nobody re-derives it, re-enables it,
> and repeats the same failures. See `00-tong-quan.en.md`, section "why they are all
> still disabled".

## Two different questions — conflating them was a real bug

```
TWO DIFFERENT QUESTIONS, and conflating them was a real bug:
  g_BigArrayOn      - has SV_AllocateEdicts been widened to 4096?
  g_EngineArray4096 - is it SAFE to actually PUT anything above 2047?

The second also requires the snapshot tables to be relocated. The first, on its
own, forces us to pin sv.max_edicts back to 2048 on every map load: with a 4096
array and max_edicts left at 4096, ED_Alloc will append ordinary NETWORKED
entities at index 2048+, which no client can address (the protocol carries only
11 bits), so they exist and respond but never get a model.
Gating the pin on the COMBINED flag meant the widened array shipped without its
safety belt.
```

## Relocating CFrameSnapshotManager's two tables

```
Move CFrameSnapshotManager's two per-entity tables out of the engine object
==========================================================================

This is the patch that makes indices above 2047 survivable at all; without it
they are not.

CFrameSnapshotManager holds two fixed 2048-entry tables inline:

    +0x009C  CPackedEntity* m_pPackedData  [2048]
    +0x209C  int            m_pSerialNumber[2048]

Seven instructions index them, none of which bounds-check - the engine has no
reason to, since a stock edict index can never exceed 2047. Writing at index
i >= 2048 therefore lands on whatever follows:

    m_pPackedData[i]   for i >= 2048  ->  m_pSerialNumber[i - 2048]
                       (SILENTLY corrupts the serial of a LOW entity - this is
                        exactly what makes an EHANDLE decode to a garbage
                        pointer and crash on the next dereference)
    m_pSerialNumber[i] for i >= 2993  ->  sv, the CGameServer object
                       (holds map state and the worldmodel pointer; once damaged,
                        the next BSP lump validation reads garbage and the engine
                        reports "Cannot load corrupted map")

So there is no safe sub-range: allocating upward corrupts serials, allocating
downward corrupts sv. Both tables MUST move somewhere with room for 4096 entries.

Every access is a 7-byte SIB form "[base + index*4 + disp32]" and rewrites to
"[index*4 + abs32]" AT EXACTLY THE SAME LENGTH, so this is an in-place edit with
no trampolines and no instruction-boundary risk:

    8B BC B1 9C 00 00 00   mov edi,[ecx+esi*4+0x9C]   -> 8B 3C B5 <packed>
    8B 84 B1 9C 20 00 00   mov eax,[ecx+esi*4+0x209C] -> 8B 04 B5 <serial>
    8B 84 91 9C 00 00 00   mov eax,[ecx+edx*4+0x9C]   -> 8B 04 95 <packed>
    8B 8C 91 9C 20 00 00   mov ecx,[ecx+edx*4+0x209C] -> 8B 0C 95 <serial>
    8B 94 B9 9C 00 00 00   mov edx,[ecx+edi*4+0x9C]   -> 8B 14 BD <packed>
    89 94 B9 9C 00 00 00   mov [ecx+edi*4+0x9C],edx   -> 89 14 BD <packed>
    89 94 B9 9C 20 00 00   mov [ecx+edi*4+0x209C],edx -> 89 14 BD <serial>

A full disassembly sweep of .text confirms these are the only SEVEN scaled-index
accesses at either displacement; the other +0x9C references belong to unrelated
objects (word-sized writes, esp-relative locals).

Missing even one would leave the engine reading one table while writing the
other, so the count is verified and the patch is ALL-OR-NOTHING.
```

## Why the engine's own clear function must NOT be patched

```
Both tables must also be cleared once per level, but NOT by editing the engine's
clear routine.

An earlier version rewrote the memset inside
CFrameSnapshotManager::LevelChanged. That broke a third-party extension:

  [SM] Unable to load extension "cutlrbtreefix.ext":
       Failed to create_inline: CFrameSnapshotManager::LevelChanged

cutlrbtreefix installs an inline hook on EXACTLY that function, finds it by
signature, and our edited bytes made the signature miss - so the extension
silently stopped loading, and the server lost a genuine engine fix it depends on.

Clearing OUR OWN table from Hook_LevelInit achieves the same result while leaving
that function byte-for-byte untouched. The engine still zeroes its now-unused
inline array, costing 8KB of memset per level and harming nothing.

THE GENERAL RULE this cost us: patch only what MUST be patched, and prefer doing
work inside your own hooks over editing a function somebody else may be hooking.
```

## Two index lookups and four abort sites

```
engine.dll has two near-identical index lookups:
  RVA 0x1E0030  IndexOfEdict      - bounds-checks against num_edicts
  RVA 0x1E0060  IndexOfEdictInfo  - bounds-checks against max_edicts
Layout of both:
  +20  cmp esi, [limit]
  +26  jl  +41              ; in range -> return the index
  +28  push "NUM_FOR_EDICT[INFO]: bad pointer"
  +33  call Error           ; FATAL - never returns
  +41  mov eax, esi ; ret

We DELIBERATELY hold max_edicts at 2048 so the engine's own allocator stays inside
the 11-bit networkable range. But the array really is 4096 entries, so a perfectly
valid edict at index 2048+ trips these checks and the engine aborts with
"NUM_FOR_EDICTINFO: bad pointer".

Turning the conditional jump into an unconditional one skips the fatal call while
still returning the correct index - the only thing lost is the bounds check, and
it is checking against a limit we intentionally understate.

Anchoring on the function prologue was A MISTAKE: it found two sites and silently
missed the rest. There are FOUR such aborts across THREE functions with different
prologues, and one of the missed ones is called by ED_Alloc itself to clear a
freshly handed-out edict - so every relocated entity trips it the moment
segregation is switched on.

The error string is the reliable anchor. Every abort site is reached by a
conditional jump sitting immediately before its "push <string>", so finding the
string references finds ALL of them regardless of function shape:

    3B 35 <limit>     cmp esi, [max_edicts]
    7C xx             jl  <in-range>        <- flip to EB, same target
    68 <string>       push "NUM_FOR_...: bad pointer"
    E8 <rel>          call Error            <- never returns

Flipping jl to jmp leaves the destination byte untouched, so control lands exactly
where the in-range case would have landed. Nothing is lost except a check against
a limit we deliberately understate.
```

```
  7C xx       jl in-range          <- the guard sits 2 bytes back
  68 <string> push "..."

  7C xx       jl in-range          <- the guard sits 3 bytes back

```

## ED_Alloc's forced-index branch

```
ED_Alloc's "forced index" path validates against num_edicts, which only counts
WHAT HAS BEEN HANDED OUT so far - so a forced index of 2048+ is always rejected.
It has to be compared against something larger.

The obvious move - point it at max_edicts and raise that to 4096 for the duration
of the call - is A TRAP. num_edicts only ever grows, and its ceiling is
max_edicts; so a single frame with max_edicts == 4096 is enough to let num_edicts
pass 2048 PERMANENTLY. TakeTickSnapshot then walks up to num_edicts while filling
a 2048-entry stack array, writes past the stack cookie, and the process dies with
no minidump and nothing on the console.

Comparing against a plain immediate removes that window entirely: no engine global
is ever mutated, so nothing can observe an inflated limit.

    3B 05 <abs32>   cmp eax, [num_edicts]   (6 bytes)
 -> 3D 00 10 00 00  cmp eax, 4096           (5 bytes) + nop

The append path further down still reads max_edicts, which stays pinned at 2048 -
so ordinary allocation cannot climb into the networkable range's upper half. Only
an EXPLICITLY forced index can reach it, and that path still checks
FL_EDICT_FREE before handing the slot over.
```

## Allocating DOWNWARD from the top of the range

```
Allocate DOWNWARD from the top of the range.

server.dll's CBaseEntityList has a SINGLE m_EntPtrArray[4096] whose upper half is
reserved for entities with NO EDICT: indices 0..2047 are written by
AddNetworkableEntity(entindex), while 2048..4095 are handed out by
AddNonNetworkableEntity() from m_freeNonNetworkableList.

Forcing an edict index of, say, 3000 makes server.dll write m_EntPtrArray[3000]
via the NETWORKED path - the very same slot its non-networkable pool may hand to
a DIFFERENT entity. Two entities then share one slot, the second overwrites the
first, and a later EHANDLE lookup passes the serial check but returns a dangling
pointer. That is exactly the observed crash: "call [vtable+0x324]" jumping into
string data.

The free list is built in ASCENDING order and popped from the head, so server.dll
consumes 2048 UPWARD. Allocating from 4095 DOWNWARD keeps the two apart until
their combined use would exceed 2048 slots - and server.dll has never needed more
than a few hundred.
```

## Marking the upper half free

```
SV_AllocateEdicts has already run for this level and, thanks to the patch above,
handed us a genuine 4096-entry array. It leaves the memory UNINITIALISED, and
FL_EDICT_FREE is a SET bit - so a zeroed slot reads as "occupied". Our half must
be marked FREE explicitly, or nothing can ever be placed there.
Stamp the upper half WHENEVER the array was widened, not only when segregation is
enabled.

SV_AllocateEdicts returns raw malloc memory, and FL_EDICT_FREE is a SET bit - so
an uninitialised slot reads as OCCUPIED, with a random m_pUnk pointer. Gating this
on segregation meant that with the array widened but segregation off, slots
2048-4095 held convincingly-live garbage for anything that reached them. Marking
them free costs one pass per level and eliminates a whole class of "reads a
perfectly plausible entity that never existed".
```

## The watchdog: TakeTickSnapshot and the stack cookie

```
A watchdog for the ONE condition that kills the process without a dump
--------------------------------------------------------------------------

TakeTickSnapshot (engine RVA 0x11D900) opens a fixed 0x1010-byte stack frame and
collects the indices of live edicts into a WORD array at [ebp-0x1004], with the
stack cookie at [ebp-4]. That leaves room for exactly
(0x1004 - 4) / 2 = 2048 entries - precisely stock max_edicts, packed with nothing
to spare.

The loop is bounded by num_edicts, which only grows, and whose ceiling is
max_edicts. So a single MOMENT of max_edicts == 4096 is enough for num_edicts to
pass 2048 PERMANENTLY for that level, and the next snapshot writes entry 2049
straight over the cookie. __security_check_cookie then fast-fails: the process
disappears with no minidump and nothing on the console - exactly the crash being
hunted.

Hook_CreateEdict raises max_edicts to 4096 around its SH_CALL, so that moment
DEMONSTRABLY exists. Rather than keep guessing, watch both values every frame and
say so the first time either leaves its safe range.
--------------------------------------------------------------------------
Watching the exact structure the server dies on
--------------------------------------------------------------------------

Every crash lands on sourcemod.2.l4d2.dll+0x13B63:

    mov ecx, [sourcemod+0xAADFC]   ; PlayerManager::m_hooks.m_Head
    mov esi, [ecx + 4]             ; m_Head->next   <-- faults here

m_hooks is a SourceHook List<IClientListener*>; its head is a 12-byte node
allocated once at DLL load, with next/prev pointing at itself when empty.
Something damages it LONG BEFORE the crash, and the crash only happens the next
time PlayerManager::MaxPlayersChanged runs - so the fault address says NOTHING
about the culprit.

Bisecting the patches has bottomed out: every switch that CAN be disabled has
been, and the crash survives all of them. So stop asking which patch is wrong and
find WHEN the structure breaks instead. Checking the ring for self-consistency
once per frame turns a delayed crash into a timestamped event, sitting next to
whatever else the log recorded at that exact instant.
```
